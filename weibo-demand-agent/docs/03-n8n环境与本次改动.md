## 2. 存储方案：不用 SQL，就用 JSON 文件

选这个的理由：

1. 你不想写 SQL —— 这里一条都没有；
2. 平台对接最终要的就是一个 `public/data/heat_perception.json` 静态快照，**存成 JSON 文件等于省掉一次转换**；
3. 用记事本 / VS Code 就能看、能改、能进 git、能截图给老师看；
4. 不额外装数据库，数据就在项目文件夹里，删目录就清空。

代价（要讲清楚，别藏着）：

- 并发写不安全 → 本项目是**单实例串行批处理**，够用；
- 数据量到几万条以上会慢 → 那时把 store 子工作流换成 `Data table` 或 Postgres，只改 1 处；
- 没有事务 → 写文件用"先写临时文件再改名"的方式兜底（P5 再实现）。

`data/` 目录里的文件规划：

| 文件 | 内容 |
|---|---|
| `posts.json` | 采集到的原始记录（去重后） |
| `items.json` | 分析结果（契约 Item 数组） |
| `run_log.json` | 每次运行一行 |
| `review_log.json` | 人工核查记录 |
| `heat_perception.json` | **给平台前端吃的快照**（最终产物） |

  -e N8N_RESTRICT_FILE_ACCESS_TO=/data `
  -e GENERIC_TIMEZONE=Asia/Shanghai -e TZ=Asia/Shanghai `
  -e N8N_SECURE_COOKIE=false `

> `N8N_SECURE_COOKIE=false` 是必要的：n8n 默认要求 https 才设 cookie，本地 `http://127.0.0.1` 会登录不上。
> **不要**删 `n8n_data` 卷，删了工作流和凭据全没。

## 6. n8n CLI 小抄（排障用）

```bash
# 列/导出工作流（含 id，用于 CLI 执行）
docker exec n8n n8n export:workflow --all --output=/data/wfs.json

# 导入工作流（JSON 里带 "id" 则更新同一条，不带则新建）
docker exec n8n n8n import:workflow --input=/data/wf.json

# 发布/取消发布（n8n 2.x 用 publish 代替 active 开关）
docker exec n8n n8n publish:workflow --id=<workflowId>
docker exec n8n n8n unpublish:workflow --id=<workflowId>

# CLI 里跑一次工作流（会因 5679 端口被占用失败，换一个 broker 端口即可）
docker exec -e N8N_RUNNERS_BROKER_PORT=5691 n8n n8n execute --id=<workflowId>

# 改了工作流的激活状态 / 发布版本后，必须重启服务端才生效
docker restart n8n
```

**两个坑**（都踩过）：

1. `n8n execute` 直接跑会报 `n8n Task Broker's port 5679 is already in use` —— 因为它想自己起一个 broker，加 `-e N8N_RUNNERS_BROKER_PORT=5691` 绕开。
2. `publish:workflow` 会明确提示 *"Changes will not take effect if n8n is running"* —— 不重启，webhook 返回的是 `404 The requested webhook is not registered`。
