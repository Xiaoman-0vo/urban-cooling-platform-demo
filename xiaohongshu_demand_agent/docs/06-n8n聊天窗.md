# 06 · n8n 聊天窗（用户自己输入的那扇门）

> 目标：让**不懂 n8n 的人**也能把自己的问题或一条微博丢进来，立刻拿到可核查的结果。
> 不是又一个 API，而是「贴一句话 → 有回答」的界面。

---

## 1. 为什么不用 n8n 自带的聊天页

n8n 官方聊天页（`POST /webhook/<hook>/chat` 那个 HTML）把样式和脚本**写死在 CDN** 上：

```html
<link href="https://cdn.jsdelivr.net/npm/@n8n/chat/dist/style.css" rel="stylesheet" />
import { createChat } from 'https://cdn.jsdelivr.net/npm/@n8n/chat/dist/chat.bundle.es.js';
```

本机实测 `cdn.jsdelivr.net` 连不上（`基础连接已经关闭: 发送时发生错误`），
打开那个页面会**白屏**——不是 n8n 坏了，是它要从公网 CDN 拉前端代码。

所以这里做两件事：

1. 把官方聊天组件（`@n8n/chat@1.44.5` 的 `chat.bundle.umd.js` + `style.css`）**放到本地** `chat/vendor/`；
2. 用一个 60 行的静态服务 `scripts/serve-chat.mjs` 托管聊天页，并把 `/webhook/*` **反向代理**到 n8n
   （同源，绕开跨域；也方便以后加口令）。

界面还是官方那套（欢迎页、气泡、Markdown、输入框），只是不再依赖外网。

## 2. 怎么用（30 秒）

双击项目根目录的 **`1-启动聊天窗.cmd`**，它会：

1. 检查 n8n 容器是否在跑，没跑就 `docker start n8n`；
2. 起本地服务 `127.0.0.1:4177`；
3. 打开浏览器 `http://127.0.0.1:4177/`。

然后直接打字。例：

| 你输入 | 走哪条路 | 耗时 |
|---|---|---|
| `成都现在有多少线索` | 读已有快照，**不调模型、不花钱** | 0.3–0.7 s |
| `重庆的诉求主要是什么` | 同上（换城市） | 0.4 s |
| `成都南站外面全是水泥地，等车热得不行` | 判定链：模型抽取 + 证据回查 | 2.5–3 s |
| `帮我抓成都 遮阴` | **下单采集**：写任务文件 → 后台工人开跑（本函数 2 s 返回） | 1.5–2 s |
| `进度` / `跑到哪了` | 读任务文件，报阶段与条数 | 0.3 s |
| `深圳有多少线索`（没采过的城市） | **自动补采**：读快照失败 → 自动下单采集 → 前台进度条跟着跑，约 2–3 分钟 | 1–2 s 回执 |
| `北京有多少线索`（采过一次之后） | 直接读 `heat_perception_北京.json` | 0.4 s |
| `你好` / `怎么用` | 用法说明（含边界） | 0.2 s |

停止：关掉那个黑色窗口，或 `Ctrl+C`。

命令行等价：

```powershell
node scripts/serve-chat.mjs --port 4178 --no-open   # 换端口、不自动开浏览器
```

## 3. 编排：`04-demand-chat`（25 个节点）

```
                      ┌─ 2a-读快照 ─2c-取文本─ 3a-回答现状 ──┐
                      │                                     │
Chat Trigger → 1-意图 ─┼─ If-开采集? ─ 2d 生成任务JSON        │
 (wc9d1f2a34b7e48c0)  │        └─2d2 转文件─2d3 写/data/jobs─┴─ 3d 回执
                      │                                     │
                      ├─ If-查进度? ─ 2e 读latest─2f 取文本 ──┴─ 3e 报进度
                      │                                     │
                      └─ If-判文本? ─ 2b-调契约(HTTP→03) ────┴─ 3b 格式化判定
                                  └─ 兜底 ─ 9-帮助 ──────────┘
```

- **1-意图**（`workflows/src/chat-1-intent.js`）：一句话读成五路意图（问现状 / 开采集 / 查进度 / 判文本 / 帮助）+ 城市 + 主题词。
  - `COLLECT_PAT`（抓/采集/爬/收集/搜…）→ **开采集**，并把"搜索词、翻几页、抓多少评论"写进任务单；
  - `STATUS_PAT`（进度/好了吗/跑到哪了…）→ **查进度**；
  - `POST_PAT` 命中（链接 / `@某人` / `#话题#` / `【】`）→ 直接判定，避免"多少"把微博正文抢成问句；
  - `HELP_PAT` 或以问候开头 → 帮助；
  - `QUERY_PAT`（多少/几条/有哪些/现状/诉求…）且带城市或"线索/诉求/数据"→ 问现状；
  - 其余 → 判定。
- **问现状分支**：`2a-读快照` 读 `data/heat_perception[_城市].json` → `3a-回答现状` 排版
  （原始条数 → 判定条数 → 落在本市 → 去重内容 → 可识别诉求 + 关切点 + 体验观察 + 边界）。
  只有成都、重庆两份快照；其他城市不读文件，直接走帮助（避免读空路径报错）。
- **判定分支**：`2b-转契约` 拼成 `action=classify` 的契约请求 → `HTTP Request` 打 **03 的正式入口**
  （而不是复制一份模型逻辑）→ `3b-格式化判定` 把契约结果排成中文。
- **9-帮助**：没看懂 / 城市没数据 / 打招呼都给这一段，含"怎么加一个城市"的三条命令。

设计取舍：**聊天层不实现模型，只做翻译与排版**。所以规则或模型改一次，聊天窗自动跟着变，
不会出现"网页判 A、接口判 B"。

## 3.5 采集任务与进度条（n8n 下单，宿主机干活）

聊天窗本身**不跑采集**：n8n 在 Docker 里，采集要读本机 Edge 的 Cookie、判定要连模型，
所以拆成"下单 — 干活 — 报进度"三方：

```
聊天窗（n8n）                 宿主机                        进度条（浏览器）
 1-意图 识别"帮我抓X Y"   →   2d3 写 /data/jobs/<id>.json   ← 每 5 s GET
 3d 回执（含任务号）           job-worker.mjs 轮询该目录        /webhook/weibo-job-status
                               ├ collect-weibo.mjs（采微博）       ↑
                               ├ run-pipeline.mjs（逐条判定）  05-job-status 读 latest.json
                               └ aggregate（汇总快照）
```

- **任务单**是 `data/jobs/<id>.json` 一个纯文本文件，字段：`query / city / pages / top / comment_pages / status / phase`。
  它同时是"队列"和"进度牌"：工人跑一步改一次，人也能直接打开看，改坏了删掉即可。
- **`latest.json`** 永远指向最近动过的任务，给"查进度"和进度条用；
  `<id>.progress.json` 是子进程写的原始进度，工人每 1.2 s 合并进任务单（避免两边同时写一个文件）。
- **进度条**在 `chat/index.html` 顶部，`position: fixed`：阶段 + 搜索词 + `N/M 条` + 百分比。
  轮询间隔：跑任务时 1.5 s，空闲时 5 s（省电、也不给 n8n 添负担）。完成 30 s 后自动收起。
- **三阶段权重**：采集 0–30%，判定 30–95%，汇总 95–100%——因为判定最久，线性映射会看着像卡住。

为什么不让 n8n 直接跑采集（用 HTTP 调微博 + Code 节点解析）：
1. Cookie 在宿主机，容器里没有；
2. 采集 1–3 分钟，n8n 的 HTTP 节点会超时，且失败重试会重复抓；
3. 采集脚本已经有成熟的重试/限速/翻页逻辑（`collect-weibo.mjs` 200+ 行），搬进节点等于重写一遍。

**启动顺序**（缺一不可）：

| 窗口 | 命令 | 作用 |
|---|---|---|
| 1 | `docker start n8n` | 界面、判定、进度接口 |
| 2 | 双击 `1-启动聊天窗.cmd` | 聊天页 + 进度条 |
| 3 | 双击 `2-启动采集工人.cmd` | 真正去采、去判、去汇总 |

## 3.5.1 缺城市自动补采（不用再手敲三条命令）

以前问一个没采过的城市，只能回一段命令让用户自己去敲。现在改成**当场下单**：

```
问「北京有多少线索」
  → 1-意图：识别出城市=北京 → 推文件名 heat_perception_北京.json，并把补采任务单（2 页 / 高温）备好
  → 2a-读快照：读不到（ENOENT）→ onError=continueRegularOutput 不让流程炸
  → 3a-汇总：拿不到文本 → 返回 { snapshot_missing: true }
  → If-缺快照? 真 → 2d 生成任务JSON → 写 /data/jobs/<id>.json → 3d 回执"已自动下单"
  → 前台进度条：采微博 → 逐条判定 → 汇总
  → 跑完写 data/heat_perception_北京.json
  → 再问一次：2a 读到了 → If-缺快照? 假 → 3a2-透传 → 正常输出数字
```

三个刻意的设计：

1. **快照存在与否由文件系统说了算**，不在代码里写死城市清单（以前写死"只有成都、重庆"，采了新城市仍回"没有"）；
2. **关键词不用问句里的原话**：先在一张小词表（遮阴/闷热/暴晒/高温…）里找热相关词，找不到用「高温」。
   否则"北京有多少线索"会把「有线索」当成搜索词；
3. **重复下单不花钱（只对自动补采生效）**：工人接到 `auto: true` 的任务，先查同搜索词
   30 分钟内有没有跑完的单，有就直接标 `deduped_from` 复用结果（连问三次也只采一次）。
   用户明确说「帮我抓…」的任务**不去重**——他要的就是新鲜数据，去重会让他以为命令没生效。

`If-缺快照?` 后面必须有 `3a2-透传`：If 节点的输出没有 `output` 字段，
聊天窗（`responseMode=lastNode`）会显示空消息——这是踩过的坑。

下面这个「3.6 局域网」之前，先记住一条：自动补采同样依赖后台工人，
工人没开时任务会停在 `queued`，进度条不会动。

### 3.5.2 词表里没有的地名，也能直接采

`config/place-lexicon.v2.json` 里的 69 个城市只是"别名更全"，不是"能不能采"的开关。
chat-1 认两种写法，认出来就把字面地名当城市名（去掉「市/区/县/镇」），别名带上全称，
worker 再把它转成 `run-pipeline.mjs --city X --aliases X市,X`：

| 说法 | 识别结果 | 结果 |
|---|---|---|
| `平顶山市现在有多少线索` | city=平顶山，aliases=[平顶山市,平顶山] | ① 无快照 → 自动下单；② 采完再问 → 出数字 |
| `平顶山现在有多少线索`（无后缀） | 同上（句首地名 + 「现在/有多少」判定） | 同上 |
| `帮我抓平顶山 遮阴` | 先剥动词"帮我抓"，再取句首地名 | 显式下单，`--city 平顶山` |
| `遮阴现在有多少线索` | 「遮阴」在主题词黑名单里 → 不当地名 | 不误判 |

实测（2026-10-28）：`平顶山市` 21 帖 / 21 评论 → 判定 20 条 → **落在平顶山 15 条**（不是全落"范围外"）
→ 去重 9 条 → 公开诉求 0 条。

没提城市时不再默默按成都回答：回执里会写明"这句里没看出城市名，先按成都那份快照回答"。

### 3.5.3 改完代码怎么让它生效（踩过的坑）

1. `python scripts/build-chat-workflow.py` → 重新生成 `workflows/04-demand-chat.json`
2. `powershell -ExecutionPolicy Bypass -File scripts/deploy-workflow.ps1 -WorkflowFile workflows\04-demand-chat.json`
3. 脚本内部做三件事：`import:workflow` → `publish:workflow --id=<按 name 查到的 id>` → `docker restart n8n`

坑：`deploy-workflow.ps1` 原来 `-BaseName` 默认写死 `03-demand-agent-api`，给 04 部署时会把 **03 的 id 注进去**，
表现是"部署成功"但线上还是旧代码。现在改成**从 JSON 文件的 `name` 强制覆盖**，并一律重新按名字取 id。
另一个坑：`publish` 之后**必须重启**容器，CLI 自己也会提示 "Changes will not take effect if n8n is running"。
## 3.6 界面（2026-10-28 改版）

深色渐变底 + 居中卡片流；顶部品牌条（标题 / 副标题 / 「样本回放，非温度观测 · 不是人数」徽标）；
Bot 气泡是带描边的毛玻璃卡片，用户气泡是青绿渐变（深色字，保证对比度）；

采集进度条改成顶部浮动卡片（流光进度、失败变红、完成后 30 秒自动收起）。
全部本地渲染（`chat/vendor/`），不引用任何 CDN——离线也能用。

三个布局细节（都是踩过才补的）：
- 整页是竖向 flex，品牌条固定高度、聊天区 `flex:1; min-height:0`——否则底部输入框会被挤出屏幕；
- 消息列表顶端对齐（组件默认贴底，欢迎页会空出上半屏）；
- 用户发过第一条之后自动收起"开始一次判读"引导（`.in-conversation`），把纵向空间还给对话。

## 3.7 换一台电脑 / 给同一局域网的人用

完整步骤见 **`deploy/README.md`**（含 docker-compose、凭据、Cookie、验收清单）。三条要点：

## 3.8 回答是怎么生成的（原文链接 + 大模型 + 说人话）

节点：`2g-构造摘要` → `2h-调摘要模型` → `3a-汇总`（都在「问现状」分支上）。

「问现状」这条分支现在是三段：

| 节点 | 干什么 | 关键约束 |
|---|---|---|
| `2g-构造摘要`（Code）| 把快照整理成 `facts`（条数、类别、代表原文、链接）并拼出模型请求体 | **数字与原文只在这里定一次** |
| `2h-调摘要模型`（HTTP）| 调 `deepseek-flash`（`response_format=json_object`，30s 超时，失败不炸流程）| 只让它组织语言，不让它算数 |
| `3a-汇总`（Code）| 渲染最终回答：一句话 / 分类明细（带链接）/ 需求 / 边界 | 模型给的类别解释对不上就丢；条数一律用 `facts` |

### 原文链接的来源与拼接规则

- 唯一来源是快照里每条记录的 `source_url`，由采集器写入：`https://m.weibo.cn/detail/<source_post_id>`；评论记录共用其**所属主帖**的链接（评论在该页下方）。
- 渲染时只接受 `http(s)://…` 形式的字符串。空值、`null`、非 URL 一律渲染成 **（原文不可访问）**，不拼接、不猜测、不留空。
- 底部会统计一行：`原文链接：N 条可跳转，M 条已缺失或已删除（标注为「原文不可访问」）`。
- 微博原文页**需要登录微博**才看得到；未登录会跳到登录页。聊天页里所有链接都用新标签打开（`target=_blank`），不会把对话顶掉。
- 「贴一条微博」那条分支没有链接可给（文本是用户粘贴的），会明确写：`原文链接：（这条是你粘贴的文本，没有可跳转的链接；可在微博里搜这句话核对）`。

### 通俗化

- 先一句大白话总结（模型生成；失败则按类别自动拼一句），再列类别与原文。
- 单条判定把术语换成人话：热相关性→**和热有关吗**、内容类型→**这是哪种说法**、空间诉求→**希望能改的地方**、评价方向→**感受倾向**、置信度→**把握有多大**。
- 不用「热相关性/空间诉求/抽样口径/维度」这类内部词；不使用「人数」，统一说「条」「机器判定条数」。

### 兜底

模型超时/报错时，回答照常出（走规则拼装），末尾注明 `（这次没能请大模型润色，上面是按规则拼的；原因：…）`——不静默、不编造。

实测（2026-10-28）：成都快照 15 条原文链接全部可跳；人为把两条 `source_url` 置空/写脏后，页面如实显示「原文不可访问」并统计 2 条缺失；回归 `scripts/test-chat.ps1` 5/5。

## 3.9 三条“看得见”的改动（2026-10-30）

### 3.9.1 模型是谁，写在回答里
每条回答最后一行固定给出：模型名、判定温度、max_tokens、规则版本、分类器版本、词表版本、地名词库版本。

- 判定（单条 / 批量）：`deepseek-flash`，`temperature=0.2`，`max_tokens=3000`，`response_format=json_object`
- 摘要（问现状那一句人话）：`deepseek-flash`，`temperature=0.3`，`max_tokens=900`
- 接口：`https://api.deepseek.com/chat/completions`（OpenAI 兼容），凭据 `httpOnly` 存在 n8n 里，名字 `DeepSeek API`
- 规则层（`2-规则层`）**不调模型**：纯歧义/广告/热搜先短路，0 成本挡掉噪声
- 想看真实调用：n8n 界面打开执行记录 → `2h-调摘要模型` / `4-调用模型`，能看到请求体与耗时

为什么不把模型名藏起来：判定与摘要都靠它，模型一换结果就会变；写进回答等于把“可复现”交给用户。

### 3.9.2 线索清单：每条都给“摘要 / 位置 / 体验 / 诉求 / 原文链接”
回答的第二段是逐条线索，顺序固定：

| 字段 | 来源 | 缺失时怎么写 |
|---|---|---|
| 原文摘要 | `items[].excerpt`（判定时截下的原文句） | 退回正文前 90 字 |
| 位置 | `place_evidence` 里 `kind=target/study_area` 的地名 | `scope_target（具体地点未指明）` / `未指明具体地点` |
| 体验 | `experience_tags` + `evaluation_direction` | `未说明` |
| 诉求 | `spatial_demands`，没有就用 `demand_topic` 兜底 | `无具体空间诉求（只说体感）` |
| 原文链接 | `source_url`（采集器写入 `m.weibo.cn/detail/<id>`） | `（原文不可访问）` |

- 只收 `heat_relevance=relevant` 且 `in_scope≠false` 的条目，按可信度排序，最多 12 条
- 位置只认目标城市的地名：顺带提到的外地（如“那年昆山和上海…”）不会被写成本条线索的地点
- 底部的「原文链接：N 条可跳转」统计的是这 12 条线索，不是全部条目

### 3.9.3 陌生城市：下单立刻有进度条
以前要等工人接单后 `latest.json` 才更新，页面在“已下单”和“还没开始”之间是空的。现在：

- 新增节点 `2d4-写进度指针`：写任务单的同时把同一份 JSON 写进 `data/jobs/latest.json`
- 状态接口因此立刻返回 `status=queued`，聊天页进度条显示 **「已下单 · 等待后台工人接单」** 并给 2% 起色
- 工人接单后同一接口变成 `running`（采集中 12% → 逐条判定 48% → 汇总 → `done` 100%）
- 城市错位也堵上了：`3a-汇总` 会比对「快照里的城市」与「用户问的城市」，不一致时回答开头直接提示

## 3.10 三处输出调整（2026-10-30 第二轮）

呼应三条反馈：输出别带「边界」、帖子别太旧、先讲温度感受再让模型摘要。

### 3.10.1 删掉输出里的「边界」
- 位置：`workflows/src/chat-3a-summary.js`（原来的 `**边界**` 小节，取 `facts.limits` 前 3 条）
- 处理：整段删除；`facts.limits` 仍留在快照里给平台侧栏用，只是聊天回答不再打印
- 保留不变：一句话、温度感受、线索清单（摘要/位置/体验/诉求/原文链接/可信度/日期）、分类明细、体验观察、需求、样本行、模型行
- 说明：一句话下面的 `>` 引用行是模型给的 caveat，不是「边界」，保留

### 3.10.2 只看最近的帖子（默认 365 天）
- 判据：**帖子发布时间**（`published_at`），不看抓取时间
- 参数：`--days N`（默认 365，0 = 不限）；两处都做
  1. `scripts/run-pipeline.mjs`：送判前就丢弃超窗内容（省钱，日志打印「时间窗 365 天：丢弃 N 条」）
  2. `scripts/aggregate-heat-perception.mjs`：聚合时再过滤一次，并把 `source.window_days / window_from` 写进快照
- 计数口径也跟着窗口走：`classified_items / in_scope_items / out_of_scope_items / place_unknown_items` 都只算窗口内
- 回答里体现：样本行会写 `发布时间 2026-05-18 ~ 2026-10-27（只算最近 365 天）`
- 为什么两处都做：采集侧的过滤保证不花钱；聚合侧的过滤保证**已有旧数据**（或别人给的 items 文件）也不会把 2024 年的帖子端上来
- 想放宽：`node scripts/run-pipeline.mjs --days 730`；想收紧演示：`--days 120`

### 3.10.3 先算温度感受，再让模型组织语言
- 第一步（规则、可复现）：`workflows/src/chat-6-facts.js` 按体感标签把窗口内帖子数一遍 → `facts.heat_feel = [{感受:'炎热'|'闷热'|'暴晒'|'凉爽/改善', 条数}]`
- 第二步（模型）：同一份材料里带上 `温度感受` 与 `时间范围`，system prompt 改成「先说温度感受（热、闷、暴晒、凉快各多少条），再说集中在什么场景/诉求」
- 渲染：`chat-3a-summary.js` 在「一句话」下面固定打印一行 `**温度感受**：炎热 22 条 · 闷热 22 条 · …`，这行**不经过模型**，模型改不了
- 效果：一句话从「大家主要在说遮阴不足」变成「说热的最多：炎热、闷热各 22 条，暴晒 5 条，另有 16 条说凉快/降温改善」

## 3.11 回答里的条数上限（可配置）

「线索清单只显示 8 条太少」这类反馈，对应的不是一个写死的 8，而是分散在三个节点的若干展示上限。
现在它们统一由 **`config/answer-caps.json`** 控制，构建时注入 Code 节点（`/*__ANSWER_CAPS__*/null` → 实际 JSON），
改完要重跑 `python scripts/build-chat-workflow.py` 并部署，才会生效。

| 上限 | 改前 | 现在默认 | 生效位置 |
|---|---|---|---|
| 线索清单条数 | 12（`chat-6-facts.js` 里的 `.slice(0, 12)`） | **40** | `facts.leads` |
| 每条线索摘要长度 | 90 字 | **120 字** | `facts.leads[].excerpt` |
| 分类明细每类代表原文 | 2 | **3** | `chat-3a-summary.js` 的 `reps_per_category` |
| 体验观察最多列几类 | 5 | **8** | `observation_categories` |
| 需求归纳条数 | 3 | **5** | `needs` |

- 回答头会写清「共 N 条，这里列 M 条；另有 N-M 条未展开，全量在平台侧栏」——**没有条数被悄悄藏起来**。
- **对已有快照的影响**：没有影响。这些是展示层上限，不改变 `heat_perception*.json` 的内容，也不用重新聚合；
  换回旧上限只要改 `answer-caps.json` 再重建部署。
- 想临时看全量：把 `leads` 调到 1000 即可（回答会很长）。

## 3.12 采集到回答的耗时（诊断，未改动）

## 5. 已知限制（写清楚，不用猜）

1. **采集要另开工人窗口。** 聊天窗只负责下单与报进度；真正干活的是 `2-启动采集工人.cmd`。
   工人没开时任务会一直停在"排队中"——这是刻意设计，避免 n8n 里跑长任务超时。
2. **只有两份快照**（成都、重庆）。其他城市需要先跑采集 + 聚合三步。
3. **回复不是温度数据。** 每条回复末尾都带边界；面板和聊天窗口径一致。
4. **重启后有 5–10 秒窗口期**：`deploy-workflow.ps1` 只等 `/webhook/weibo-demand/v1` 就绪，
   聊天钩子可能再晚几秒。测试脚本已内置预热重试。
5. **无鉴权**。`serve-chat.mjs` 只监听 `127.0.0.1`，等于"只给本机用"。要给别人用，
   先在代理层加口令/`X-Api-Key`，别直接把 5678 暴露到公网。
6. **vendor 是第三方代码**（`@n8n/chat@1.44.5`，MIT）。升级：`npm pack @n8n/chat` 后
   把 `dist/chat.bundle.umd.js` 与 `dist/style.css` 覆盖进 `chat/vendor/`。

## 6. 排障

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面白屏 | 直接开了 n8n 的 `/webhook/.../chat`（依赖 CDN） | 用 `http://127.0.0.1:4177/` |
| `n8n 不可达` | 容器没起 | `docker start n8n`，再刷新 |
| 回复一直是"没看懂" | `1-意图` 路由没命中 | 换说法（带城市或"线索/诉求"），或看 n8n 执行记录里 `1-意图` 的 `intent` |
| 判定很慢（>20 s） | 模型排队/网络抖动 | 重试；批量判走 `run-pipeline.mjs` 更稳 |
| 端口 4177 被占 | 上次的窗口没关 | `--port 4178` 或杀掉旧 node 进程 |
| 进度条一直 0% 或停在「排队中」 | 采集工人没开 | 双击 `2-启动采集工人.cmd` |
| 进度条不出现 | `05-job-status` 没部署 | `deploy-workflow.ps1 -WorkflowFile workflows\05-job-status.json -BaseName 05-job-status` |
