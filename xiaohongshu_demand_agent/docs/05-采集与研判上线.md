## 二、采集链（脚本版，先跑通再搬进 n8n）

```
refresh-cookie.ps1  →  .weibo-cookie / .weibo-cookie-web
        ↓
collect-weibo.mjs   →  data/raw_weibo.json
        ↓
classify-samples.mjs → n8n /webhook/weibo-demand/v1  →  data/classified_weibo.json
```

### 2.1 三个接口（都实测过）

| 用途 | 接口 | 鉴权 | 限制 |
|---|---|---|---|
| 搜索 | `https://m.weibo.cn/api/container/getIndex?containerid=100103type=1&q=<词>&page_type=searchall&page=N` | `.weibo.cn` 的 cookie | 每页 10 条；`cardlistInfo.total` 只是平台自报 |
| 一级评论 | `https://weibo.com/ajax/statuses/buildComments?id=<mid>&count=20&flow=1&max_id=<cursor>` | `.weibo.com` 的 cookie + `X-XSRF-TOKEN` | 每页 20 条；`flow=1` 按热度、`flow=0` 按时间 |
| 长文补全 | `https://m.weibo.cn/statuses/extend?id=<mid>` | 同搜索 | 仅 `isLongText` 时调用 |

不能用的：热搜榜 `weibo.com/ajax/side/hotSearch` 匿名可读，但**与选址无关**；
`/api/comments/show` 返回空壳（已弃用），不要浪费时间。

### 2.2 Cookie 为什么必须这么取

- 搜索与评论**必须登录态**，匿名会跳 `visitor.passport.weibo.cn`。
- Edge 140 把 cookie 升级成 **v20（应用绑定加密）**：用 DPAPI 主密钥解 `encrypted_value` 会全部失败，
  只有浏览器自己能解。**可行路径只有 CDP**。
- `refresh-cookie.ps1` 做的事：确认 9222 调试端口 → `Storage.getCookies` → 按域写两个文件。
- 需要 `--remote-debugging-port` 重启 Edge（脚本 `-LaunchEdge` 自动做，会恢复上次会话）。

> 这两个 cookie 文件已在 `.gitignore` 里。**不要提交、不要发群、不要写进截图。**
> 登录态通常几天到几周过期，报「跳登录页」就重跑一次 `refresh-cookie.ps1`。

### 2.3 限速红线（写进代码的默认值）

- 请求间隔 `--pace 1500ms`（评论与搜索共用）；
- 单次运行 ≤ 100 次请求；
- 失败重试 3 次指数退避；
- 只读公开内容，**不抓私信、不抓关注关系、不做自动化登录**。

## 三、研判链（n8n 里的四个环节）

```
Webhook → 1-契约校验 → 2-规则层 →┬→ [rule_only] → Respond（不调模型）
                                  └→ If-需要模型? ─┬→ 3-构造模型请求 → 4-调用模型 → 5-校验与合并 → Respond
                                                   └→ [health/rule_only/契约错] → Respond
```

### 3.1 分工

| 环节 | 谁在做 | 决定什么 |
|---|---|---|
| 规则层 | 关键词 + 决策顺序（`config/taxonomy.v1.json`） | 哪些**不该花钱**（歧义词短路）、预标注提示 |
| 模型层 | `deepseek-flash`（`response_format=json_object`, T=0.2） | 读出结构化线索（话题/情感/诉求/可操作度） |
| 校验层 | 确定性代码 | 枚举越界丢弃、证据回查、置信度合成、是否进人工队列 |

### 3.2 五条防「模型胡说」的硬规则

1. 枚举只能从词表选，越界值直接丢并记 `model_notes`；
2. `evidence_spans[].quote` 必须能在原文 `indexOf` 到，找不到就作废；
3. **判为 relevant 但没有任何可回查证据 → 强制降级 `needs_review`**；
4. 规则只命中歧义词而模型说相关 → 降级 `needs_review`；
5. 置信度由确定性依据合成（`span_valid` / `rule_hit` / `rule_agrees` / `public_demand` / 扣分项），
   **不用模型自报的概率**。

### 3.3 置信度公式（可复算）

```
base 0.40
+0.20 至少一个证据片段回查成功
+0.10 规则层命中过热环境词
+0.10 规则与模型方向一致
+0.10 判为相关且是可被公共空间回应的诉求
-0.15 仅命中歧义词
-0.05 命中否定标记
-0.15 判相关但零证据
→ clamp[0.05, 0.92]；≥0.80 high，≥0.65 medium
```

## 五、已知短板（接下来要处理的，不是 bug 但会被问）

1. ~~没有城市范围过滤~~ → **已修**：请求里带 `payload.scope.city`，规则层按词表判 `location_scope`
   （`target` / `other_place` / `unknown`），并给出 `in_scope`；不传 scope 就不做过滤（通用模式）。
   见本文第七节。
2. **天气播报占多数**：气象博主的帖子会带大量「高温」词，虽然 `is_public_demand=false`，
   但会稀释民意密度。→ 采集查询应偏向体感词（闷/晒/遮阴/等车/凉快），而不是「高温」。
3. **串行慢**：一条 2–6 s，20 条要 1 分钟。→ P5 用 `extract_batch` + 分批并发（同步上限 20 条/60 s）。
4. **长文只取前 2000 字**：可能丢后段的诉求。→ 先按段落切分再逐段判，或对长文抽首尾。
5. **没有去重与转发归并**：同一事件的多条转述会重复计数。→ P5 做 `content_hash` 近似去重 + 事件聚类。
6. **接口是网页端私有接口**：随时可能变。→ 采集失败必须落「受限或延迟」状态，不能装作没数据。

## 六、合规与答辩口径

- 只用**公开可见**内容，不绕过登录、不破解加密、不抓私信；
- Cookie 只存在本机、只用于本次研究，**不共享、不入库、不展示**；
- 产物是「公众表达线索」，**不是** 温度观测、不是受影响人数、不是总体民意；
- 采样方式为关键词检索（非随机抽样），报告里必须写明这一点和样本量。

### 7.3 动作收口：不认识的请求不许"假装成功"

`1-契约校验` 现在按 `action` 校验必填字段，并在动作未接入时直接返回 **501 + `E_NOT_IMPLEMENTED`**：

| action | 状态 |
|---|---|
| `health` / `classify` | 已接入 |
| `extract_batch` / `query_items` / `review` | 契约已声明、工作流侧未实现 → 501，`detail.implemented` 列出可用动作 |

为什么必须这样：之前 `query_items` 会一路落到 `classify`，拿 `undefined` 去跑模型，
返回一个"看似成功的空结果"——这比报错更危险。
